# 模型用量数据契约（v1）

> 状态：已定稿（第一阶段基线）。实现以本文档为权威；`schema/usage.schema.json`、`src/types.ts` 中的用量类型、加载校验与只读 API 必须与本文档保持一致。口径计算规则见《成本核算规则.md》。

## 1. 目的与范围

本契约定义版本计划工具如何以**独立账本文件**记录与校验模型用量：每次模型调用登记为一个事件（event），与需求池中的真实任务关联，携带 Token 明细、角色、来源、可信状态与可选费用依据。

- 解决四个问题：每个任务有哪些模型参与、各模型消耗多少 Token、主控/开发/验收/返工分别消耗多少、哪些成本有账单依据哪些只是估算。
- 工具保持**只读**：本契约不引入任何写接口、模型调用或自动采集能力。数据由消费项目侧提供。
- 工具保持**通用**：不预设供应商清单、模型清单、角色清单、阶段名称。消费项目通过可选扩展 Schema 施加项目特定约束。

## 2. 术语

| 术语 | 含义 |
|---|---|
| 用量账本（usage ledger） | 独立的 JSON 文件，包含 `prices` 与 `events` 两张表 |
| 事件（event） | 一次模型调用的登记记录，是全账本的最小计费与统计单元 |
| 价格版本（price） | 一条单价记录，绑定模型、计价单位、币种、有效期与依据 |
| 任务（task） | 需求池（roadmap）中的一个 requirement，事件通过 `taskId` 关联 |
| 实际费用 | 有供应商账单或可靠实际费用数据为依据的费用 |
| 估算费用 | 按已知单价与用量明细、依《成本核算规则.md》公式算出的费用 |
| 未知费用 | 用量或价格依据不足、无法可靠核算的费用 |

## 3. 配置方式

### 3.1 配置字段

在消费项目的 `version-plan.config.json` 中新增**可选**字段 `usageFile`：

```json
{
  "dataFile": "版本计划/需求池.json",
  "schemaFile": "版本计划/需求池.schema.json",
  "usageFile": "版本计划/模型用量.json"
}
```

- `usageFile`：字符串，指向用量账本 JSON，必须是消费项目内的相对路径。
- 该字段遵循与 `dataFile`、`schemaFile` 完全相同的路径安全校验（见 §8）。
- 字段白名单从 `dataFile`/`schemaFile` 扩展为 `dataFile`/`schemaFile`/`usageFile`；配置中出现其他字段仍然报 `CONFIG_INVALID`。

### 3.2 兼容规则（硬约束）

| 场景 | 行为 |
|---|---|
| 未配置 `usageFile` | 不加载用量。CLI、页面与既有 API 字段及其语义保持兼容（行为不变）；API 响应按新契约附带 `usage: null`（新增字段，既有字段值不变） |
| 配置了 `usageFile`，文件缺失或不可解析 | 明确诊断 `USAGE_FILE_INVALID`，校验失败（退出码 1） |
| 配置了 `usageFile`，文件存在但不符合 Schema | `USAGE_SCHEMA_INVALID` 诊断，校验失败 |
| 文件存在但项目未配置 `usageFile` | 不加载、不报错、无副作用 |

**兼容性判定标准（修订 v1.1）**：旧项目兼容指**功能行为兼容**——CLI 命令与退出码、页面加载与交互、既有 API 字段的值与语义均不改变；不承诺 HTTP 响应字节不变。API 响应新增 `usage: null` 是本契约的组成部分，属于有意的前向兼容变更：老消费者忽略未知字段即可，新消费者可据此区分"未启用账本"与"启用但无数据"。该边界必须由回归测试确认（见 §14 T01）：旧版页面加载、CLI 校验、既有 API 字段值逐项断言。

账本文件本身允许为空表（`events: []`）：启用但暂无数据是合法状态，UI 显示空态而非错误。

## 4. 账本文件结构

### 4.1 顶层结构

```json
{
  "schemaVersion": 1,
  "project": "game-agent-harness",
  "prices": [],
  "events": []
}
```

- `schemaVersion`：整数常量 `1`。契约演进时升版本，旧版本文件必须显式报错，不做静默迁移。
- `project`：可选字符串。若提供，必须与需求池 `project.id` 一致，否则报 `USAGE_PROJECT_MISMATCH`。防止把 A 项目的账本接到 B 项目上。
- `prices`：可选数组，价格版本表（§5）。
- `events`：必填数组，调用事件表（§6）。允许为空数组。

- 供应方、模型、角色均为自由非空字符串，不设枚举——通用性由扩展 Schema 兜底（见 §9）。

## 5. 价格版本表（prices）

每条 price 是一条**不可变的价格快照**：

| 字段 | 类型 | 语义 |
|---|---|---|
| `id` | string | 价格版本唯一 ID |
| `provider` | string | 供应方，与事件的 `provider` 同口径 |
| `modelId` | string | 模型标识，与事件的 `modelId` 同口径 |
| `currency` | string | ISO 4217 三位大写字母，如 `CNY`、`USD` |
| `unitTokens` | integer ≥ 1 | 单价的计价 token 数，如 `1000000` 表示每百万 token |
| `inputPricePerUnit` | number ≥ 0 | 每 `unitTokens` 个输入 token 的单价 |
| `cachedInputPricePerUnit` | number ≥ 0 | 可选；缓存输入单价。缺失时的处理见《成本核算规则.md》§3.3 |
| `outputPricePerUnit` | number ≥ 0 | 每 `unitTokens` 个输出 token 的单价 |
| `reasoningPricePerUnit` | number ≥ 0 | 可选；推理 token 单价。缺失时回退 `outputPricePerUnit`（见核算规则 §3.3） |
| `effectiveFrom` | date-time | 生效起始时间（含） |
| `effectiveTo` | string \| null | 生效结束时间（不含）；`null` 表示至今有效 |
| `basis` | string | 不可变依据描述，如"供应商定价页快照 2026-10-01，URL …"。**必填** |
| `note` | string | 可选备注 |

规则：

1. **只增不改**：历史费率变化时新增一条 price（新 `effectiveFrom`），禁止修改已有 price 的任何字段——既有事件的计价依据因此保持可追溯。
2. **同模型不重叠**：同一 `(provider, modelId)` 的两条 price 有效期不得重叠，否则 `USAGE_OVERLAPPING_PRICE`。
3. **区间合法**：`effectiveTo` 不得早于等于 `effectiveFrom`，否则 `USAGE_INVALID_PRICE_WINDOW`。
4. `basis` 是审计锚点：没有依据的单价不允许进账本。
5. **显式引用同样受有效期约束（修订 v1.1）**：事件的 `priceId` 与 `cost.priceId` 显式引用某条 price 时，必须四要素一致——`provider` 一致、`modelId` 一致、且 `occurredAt` 落在该 price 的 `[effectiveFrom, effectiveTo)` 区间内（`effectiveTo = null` 视为开放区间）。任一不满足即报稳定诊断（`USAGE_PRICE_MODEL_MISMATCH` / `USAGE_PRICE_NOT_EFFECTIVE`），**不得静默按过期或错配价格估算**。自动匹配路径天然只匹配时间窗内的价格；显式引用没有这个保护，因此必须显式校验。

## 6. 调用事件表（events）

### 6.1 字段语义

| 字段 | 类型 | 必填 | 语义 |
|---|---|---|---|
| `id` | string | 是 | 事件唯一 ID，建议 `evt-` 前缀 + 全局唯一串。重复即 `USAGE_DUPLICATE_EVENT_ID`，用于幂等去重 |
| `taskId` | string | 是 | 关联需求池 requirement ID。不存在即 `USAGE_UNKNOWN_TASK` |
| `occurredAt` | date-time | 是 | 调用发生时间（ISO 8601 带时区） |
| `provider` | string | 是 | 模型供应方标识 |
| `modelId` | string | 是 | 实际模型标识（供应方口径，如具体版本号） |
| `agent` | string \| null | 否 | Agent 标识或名称（实例名、子代理名） |
| `role` | string | 是 | 承担角色，自由字符串。推荐词表见 §6.2 |
| `source` | enum | 是 | 用量来源：`provider`（供应商返回）、`runtime_log`（运行日志）、`manual`（人工登记）、`estimate`（估算） |
| `confidence` | enum | 是 | 可信状态：`measured`（实际记录）、`estimated`（估算）、`unknown`（未知） |
| `usage` | object | 是 | Token 明细，见 §6.3 |
| `priceId` | string | 否 | 显式绑定的价格版本 ID（快照引用）。缺省时按 `(provider, modelId, occurredAt)` 匹配 |
| `cost` | object | 否 | 人工登记的货币费用，见 §6.4 |
| `note` | string | 否 | 备注 |

### 6.2 角色词表（推荐，非 Schema 强制）

工具不强制角色枚举。消费项目按治理规范自选词表；Game-Agent-Harness 的推荐词表：

- `主控协调`：主控协调角色的调用
- `开发执行`：开发角色的调用
- `独立验收`：独立验收角色的调用
- `返工`：返工修复的调用

项目可在自己的用量账本扩展约束（通过文档约定或后续工具机制）施加枚举；工具本身保持开放。

### 6.3 Token 明细与口径（硬规则）

```json
"usage": {
  "inputTokens": 12000,
  "outputTokens": 3000,
  "cachedInputTokens": 8000,
  "reasoningTokens": 1200
}
```

- `cachedInputTokens` 是 `inputTokens` 的**细分项**（缓存命中部分已包含在输入总量内）。
- `reasoningTokens` 是 `outputTokens` 的**细分项**（推理产出已包含在输出总量内）。
- **汇总时四个字段分别累加，绝不把细分项再加到总量上。** 总输入 = ΣinputTokens；总输出 = ΣoutputTokens。缓存、推理只在明细视图展示。
- 交叉约束（语义层校验，Schema 不表达）：`cachedInputTokens ≤ inputTokens`，`reasoningTokens ≤ outputTokens`，违反报 `USAGE_TOKEN_SUBTOTAL_EXCEEDED`。
- 不符合"细分包含"口径的来源数据，必须在导入本账本前完成转换（如供应商把缓存单列在总量外，登记时须合并进 `inputTokens` 并填 `cachedInputTokens`），转换规则在事件 `note` 或项目文档中说明。工具不猜。

### 6.4 人工登记费用（cost）

```json
"cost": {
  "basis": "actual",
  "currency": "CNY",
  "amount": 0.0372,
  "priceId": "deepseek-chat-2026-10",
  "note": "供应商账单 2026-10 月结对账",
  "assumptions": []
}
```

- `basis: "actual"`：该金额有供应商账单或可靠实际费用依据，`note` 应说明依据。
- `basis: "estimated"`：登记者自行估算的金额（例如使用了工具公式之外的计费）。此时 `assumptions` 列出所做假设。
- `amount` 在两种 basis 下都必填于展示层；Schema 不强制（允许先登记骨架后补），但**缺 `amount` 的记录在汇总中按 unknown 处理，不得当作 0**。
- `cost.priceId` 若提供，必须存在于 `prices` 且 `(provider, modelId)` 与事件一致，币种必须与 price 的 `currency` 一致，否则 `USAGE_CURRENCY_MISMATCH` / `USAGE_PRICE_MODEL_MISMATCH`。

### 6.5 事件费用口径的唯一性（防双重计费）

一条事件的最终费用按优先级唯一确定：

1. 事件带 `cost`（actual 或 estimated）→ 以登记为准；
2. 否则工具按价格版本与公式自动估算 → `estimated`；
3. 否则 → `unknown`。

actual 与 estimated **只在汇总层分列展示，永不相加**；一条事件不会同时进入两个桶。

### 6.6 两个价格引用字段的职责（修订 v1.1）

| 字段 | 职责 | 生效场景 |
|---|---|---|
| 顶层 `priceId` | **估算快照引用**：固定该事件自动估算所用的价格版本 | 事件无 `cost` 时，工具按它（而非按时间窗自动匹配）估算 |
| `cost.priceId` | **登记费用的计价依据引用**：说明登记的 `cost.amount` 是按哪个价格版本算出的（审计锚点） | 事件带 `cost` 时；不改变"以登记金额为准"的结论 |

组合规则：

1. 允许只有顶层 `priceId`（自动估算固定快照，无登记费用）；
2. 允许只有 `cost.priceId`（登记费用及其依据，顶层不固定快照）；
3. 允许两者同时存在**且一致**（登记金额同时固定估算快照——例如按账单登账后补挂快照）；
4. **不允许两者同时存在且不一致** → `USAGE_PRICE_REF_CONFLICT`。同一事件引用两个不同价格版本属于数据矛盾，不静默择一；
5. `cost.priceId` 与顶层 `priceId` 适用同一套引用校验（§5 规则 5：provider / modelId / 有效期四要素）；
6. 费用口径唯一性规则（§6.5）不变：`cost` 优先于自动估算；一条事件只进入 actual / estimated / unknown 之一，不重复计费。

测试见 §14 T11（只有顶层 / 只有 cost.priceId / 两者不一致三组反例，加两者一致一组正例）。

## 7. 校验规则与诊断码

### 7.1 Schema 层（Ajv，`USAGE_SCHEMA_INVALID`）

结构、类型、必填、枚举、非负整数、`additionalProperties` 全部由 §4.2 Schema 执行，错误信息沿用现有 `schemaDiagnostics` 格式。

### 7.2 语义层（`validateSemantics` 扩展）

| 诊断码 | 触发条件 | path 示例 |
|---|---|---|
| `USAGE_DUPLICATE_EVENT_ID` | 事件 ID 重复 | `/events/<id>` |
| `USAGE_DUPLICATE_PRICE_ID` | 价格 ID 重复 | `/prices/<id>` |
| `USAGE_UNKNOWN_TASK` | `taskId` 不在需求池 requirements | `/events/<id>/taskId` |
| `USAGE_UNKNOWN_PRICE` | `priceId` 或 `cost.priceId` 引用不存在的价格 | `/events/<id>/priceId` |
| `USAGE_PRICE_MODEL_MISMATCH` | 引用的 price 与事件的 `(provider, modelId)` 不一致 | `/events/<id>/priceId` |
| `USAGE_PRICE_NOT_EFFECTIVE` | 显式引用的 price 有效区间不含事件的 `occurredAt`（含 `cost.priceId`） | `/events/<id>/priceId`、`/events/<id>/cost/priceId` |
| `USAGE_PRICE_REF_CONFLICT` | 事件同时带顶层 `priceId` 与 `cost.priceId` 且两者不同（职责见 §6.6） | `/events/<id>/priceId` |
| `USAGE_CURRENCY_MISMATCH` | 事件币种与所引用 price 的币种不一致 | `/events/<id>/cost/currency` |
| `USAGE_TOKEN_SUBTOTAL_EXCEEDED` | `cachedInputTokens > inputTokens` 或 `reasoningTokens > outputTokens` | `/events/<id>/usage/...` |
| `USAGE_INVALID_PRICE_WINDOW` | `effectiveTo ≤ effectiveFrom` | `/prices/<id>` |
| `USAGE_OVERLAPPING_PRICE` | 同 `(provider, modelId)` 价格有效期重叠 | `/prices/<id>` |
| `USAGE_PROJECT_MISMATCH` | 账本 `project` 与需求池 `project.id` 不一致 | `/project` |
| `USAGE_FILE_INVALID` | 配置了 `usageFile` 但文件缺失或 JSON 不可解析 | 文件路径 |

### 7.3 不构成错误的状态（正常数据，UI 展示未知）

- 事件没有 `cost`、没有 `priceId`、时间窗内也没有匹配价格 → 费用 `unknown`，Token 照常统计。
- 事件 `confidence: "unknown"` → 允许存在，汇总时按低可信标记，不阻断。
- 账本 `events: []` → 空态。

### 7.4 不完整记录规则（硬规则）

- Token 字段不允许省略来表达"未知"——Schema 必填。确实不知道 Token 的调用**不得登记为 0**：要么补一个 `confidence: "estimated"` 的估计值并注明，要么不登记（留待自动采集阶段）。
- `cost` 缺 `amount` 的事件进入 `unknownCostEvents` 计数，不按 0 元计入任何费用合计。

## 8. 路径安全

`usageFile` 与 `dataFile`/`schemaFile` 共用 `resolveProjectFile`：拒绝绝对路径、`..`、Windows ADS、越界符号链接与不存在路径。用量账本不获得任何超出既有数据文件的读取能力。配置解析失败统一报 `CONFIG_INVALID`。

## 9. 与需求池的关联

- 事件通过 `taskId` 关联 requirement；账本自身不复制任务结构，不在需求池任务上增加 `model`/`tokens` 字段。
- 一个任务可有多个事件、多个角色、多个模型；一个模型可参与多个任务——Schema 不施加任何唯一性约束（事件 ID 除外）。
- 需求池变更（任务取消、ID 重编）后，历史事件的 `taskId` 可能悬空 → `USAGE_UNKNOWN_TASK`。这是有意的严格：账本必须与需求池同源维护，悬空即修复数据，不静默丢弃。

`GET /api/roadmap` 响应在现有结构上扩展一个可选字段：

```json
{
  "valid": true,
  "diagnostics": [],
  "data": { "...": "roadmap 原样" },
  "usage": {
    "enabled": true,
    "ledger": {
      "schemaVersion": 1,
      "project": "game-agent-harness",
      "prices": ["..."],
      "events": ["..."]
    },
    "summary": {
      "totals": { "...": "UsageBucket" },
      "byTask": { "P3-01": { "...": "UsageBucket" } },
      "byRelease": { "v0.3": { "...": "UsageBucket" } },
      "byModel": { "deepseek/deepseek-chat": { "...": "UsageBucket" } },
      "byProvider": { "deepseek": { "...": "UsageBucket" } },
      "byRole": { "开发执行": { "...": "UsageBucket" } }
    }
  }
}
```

- 未配置 `usageFile` 时，响应在既有字段（`valid` / `diagnostics` / `data`）之外附带 `usage: null`；既有字段及其值不变（兼容性定义见 §3.2）。
- 配置了但账本校验失败时，`usage` 为 `null` 且 `diagnostics` 中含用量诊断码；页面按现有失败态展示。
- `UsageBucket` 结构：

```json
{
  "eventCount": 12,
  "taskCount": 3,
  "modelCount": 2,
  "tokens": {
    "input": 120000,
    "output": 30000,
    "cachedInput": 80000,
    "reasoning": 12000
  },
  "confidence": {
    "measured": {
      "eventCount": 10,
      "tokens": {
        "input": 100000,
        "output": 25000,
        "cachedInput": 70000,
        "reasoning": 10000
      }
    },
    "estimated": {
      "eventCount": 1,
      "tokens": {
        "input": 10000,
        "output": 2500,
        "cachedInput": 5000,
        "reasoning": 1000
      }
    },
    "unknown": {
      "eventCount": 1,
      "tokens": {
        "input": 10000,
        "output": 2500,
        "cachedInput": 5000,
        "reasoning": 1000
      }
    }
  },
  "costActual": { "CNY": 0.37 },
  "costEstimated": { "CNY": 1.85 },
  "unknownCostEventCount": 2,
  "assumptions": ["cached_input_price_fallback_to_input"]
}
```

- `tokens.input/output` 为口径总量；`cachedInput/reasoning` 为细分明细，**不再计入总量**。
- `costActual`/`costEstimated` 按币种分列，不同币种不相加。
- `assumptions` 汇总该桶涉及的全部估算假设标识，供统计口径说明展示。回退假设的**触发条件**（分段 Token 为零时不记录）见《成本核算规则.md》§3.3 回退假设记录规则。
- `confidence`（修订 v1.1）：按事件的可信状态分三组的**分组视图**，规则：
  - 三组互斥且完备——每个事件按 `confidence` 归入且仅归入一组（`measured` / `estimated` / `unknown`）；
  - 三组 `eventCount` 之和恒等于桶的 `eventCount`；三组 `tokens` 逐字段之和恒等于桶的 `tokens` 对应字段；
  - **子汇总不得与总量再次相加**（与缓存/推理细分同一规则）——它们是分组视图，不是额外消耗；
  - 用途：让界面能可靠解释"总消耗中有多少调用属于低可信记录"。UI 的统计口径说明必须展示三组事件数及低可信（`estimated` + `unknown`）占比，测试见 §14 T12。

汇总函数为纯函数（`src/usage.ts`），CLI、服务、前端共用同一实现，保证任务明细、版本汇总、模型统计数值一致。汇总键：

- `byTask`：任务 ID；
- `byRelease`：任务的 `releaseId`（无任务的悬空事件在校验层已被拦截，不会进入汇总）；
- `byModel`：`provider/modelId`；
- `byProvider`：`provider`；
- `byRole`：`role`。

## 12. 第一阶段明确不做

- 不从 API 返回值、运行日志或供应商账单自动导入；自动采集待独立立项。
- 不提供写接口、模型调用、订阅套餐折算、汇率转换。
- 不引入供应商/模型/角色枚举到工具 Schema（通用性约束）。
- 不在需求池任务结构上增加模型或 Token 字段。

## 13. 变更规则

- 本契约的任何修改必须升 `schemaVersion` 或在同版本内保持向后兼容，并同步更新：`schema/usage.schema.json`、`src/types.ts`、加载校验、只读 API、UI、测试与 README。
- 契约修改按工具仓库自身的任务与测试流程完成，不得在消费项目仓库内顺手改工具源码。
- §14 测试矩阵是实现的验收基线：开发代理按矩阵实现并自证，独立验收代理按矩阵**逐项独立检查**（含对修订 v1.1 四项的专项核验），不得仅凭文档新增说明判为通过。
